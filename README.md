## Parte 3 — Perguntas de reflexão

### 1. Injeção de dependência (Aula 13)
Os controllers (`ConteudoController`, `UsuarioController`, `AluguelController`) recebem os repositories via `@Autowired`, e não via `new ConteudoRepository()`, porque `ConteudoRepository` é uma **interface** — `interface ConteudoRepository extends JpaRepository<Conteudo, Long>`. Não existe uma classe concreta escrita por nós para instanciar com `new`; quem gera a implementação em tempo de execução (um proxy dinâmico que sabe conversar com o banco) é o próprio Spring Data JPA, ao subir o contexto da aplicação. O Spring cria esse bean uma única vez, gerencia seu ciclo de vida e o entrega pronto para qualquer classe que declare precisar dele (via `@Autowired`), sem que o controller precise saber como o repository foi construído nem se preocupar em recriá-lo a cada requisição. Se tentássemos `new ConteudoRepository()`, o código nem compilaria (não dá para instanciar uma interface diretamente), e mesmo que fosse uma classe concreta, perderíamos a configuração automática de conexão com o Oracle, transações e o gerenciamento de ciclo de vida que o Spring faz por trás.

### 2. JDBC vs Spring Data JPA (Aulas 12 e 13)
No `ProdutoDAO` da Aula 12, cada operação (buscar, salvar, listar) exigia escrever manualmente `Connection`, `PreparedStatement`, montar o SQL como string, executar, percorrer o `ResultSet` e mapear cada coluna para os atributos do objeto — inclusive tratar `SQLException` e fechar os recursos. Aqui, `ConteudoRepository extends JpaRepository<Conteudo, Long>` tem duas linhas e já ganha `save`, `findById`, `findAll`, `deleteById` prontos: o Spring Data JPA gera a implementação e o SQL sozinho, usando a anotação `@Entity`/`@Table`/`@Id` de `Conteudo` para saber como mapear objeto-tabela. O `findByCategoria(String categoria)` funciona sem nenhuma implementação porque o Spring Data JPA interpreta o **nome do método** (`findBy` + `Categoria`) e gera a query (`WHERE categoria = ?`) automaticamente — é a convenção "query derivation". O que o JDBC/DAO ainda resolve melhor é controle fino: SQL customizado complexo, tuning de performance específico, ou quando não se quer o overhead do ORM; para CRUD e consultas simples como as deste projeto, o Spring Data JPA elimina código repetitivo (boilerplate) sem perder a segurança de tipos.

### 3. Exceções checked vs unchecked (Aula 11)
`ClassificacaoIndicativaException` originalmente estendia `Exception` (checked). Uma checked exception obriga quem a lança a declarar `throws` na assinatura do método (como estava em `Usuario.alugar(Conteudo c) throws ClassificacaoIndicativaException`), e o compilador força quem chama a tratá-la ou repassá-la. O problema é que, dentro de um método de controller do Spring (`@PostMapping`), quando uma exceção checked "escapa" sem ser tratada, o Spring MVC a encapsula como erro interno do servidor (`500`) por padrão, e como não havia nenhum `@ExceptionHandler` para ela em `GlobalExceptionHandler`, a mensagem de negócio ("Usuário de X anos não pode assistir a Y") nunca chegava formatada ao cliente da API — só um erro genérico. A correção foi alterar `ClassificacaoIndicativaException` para estender `RuntimeException` (unchecked, como as demais exceções de negócio do projeto: `ConteudoIndisponivelException`, `CreditosInsuficientesException`), remover os `throws` que ficaram desnecessários, e adicionar um `@ExceptionHandler(ClassificacaoIndicativaException.class)` em `GlobalExceptionHandler` retornando `403 Forbidden` com a mensagem da exceção no corpo da resposta. Unchecked exceptions de regra de negócio, tratadas de forma centralizada via `@RestControllerAdvice`, são o padrão usado em toda a API deste projeto.

### 4. Sobrescrita vs sobrecarga (Aula 7)
O bug02 é exatamente esse caso: `Conteudo` declara `public double calcularPrecoAluguel()` (sem parâmetros), e `Serie` declarava `public double calcularPrecoAluguel(double desconto)` (com um parâmetro `double`). Como as assinaturas são diferentes (o número/tipo de parâmetros muda), o Java não entende isso como uma sobrescrita (override) do método do pai — entende como um método **novo**, uma sobrecarga (overload) que coexiste com o método herdado. Resultado: quando o código chamava `conteudo.calcularPrecoAluguel()` (sem argumentos, como em `Usuario.alugar` e `Conteudo.calcularPrecoPromocional`), o Java continuava resolvendo para a implementação padrão de `Conteudo` (9.90 fixo), e o método "customizado" de `Serie` simplesmente nunca era chamado por ninguém — o código compilava perfeitamente porque, do ponto de vista do compilador, não havia erro nenhum, só dois métodos com nomes iguais e assinaturas diferentes. Se o método de `Serie` tivesse a anotação `@Override`, o compilador teria acusado erro de compilação imediatamente (`method does not override a method from its superclass`), porque `@Override` instrui o compilador a verificar que aquele método realmente corresponde a um método da superclasse/interface com a mesma assinatura — é exatamente por isso que, depois da correção, adicionamos `@Override` em todos os métodos que sobrescrevem algo no projeto (clean03 tangencia esse cuidado).

### 5. Onde blindar o objeto? (Aulas 3, 4 e 13)
Encontramos dados inválidos aceitos em pelo menos dois pontos: `duracaoMinutos <= 0` (bug09) e o saldo de créditos podendo ficar negativo (bug04). A validação de `duracaoMinutos` foi colocada no **construtor** de `Conteudo`, porque é o único ponto por onde toda subclasse concreta (`Filme`, `Serie`, `Documentario`) obrigatoriamente passa ao ser criada — colocar a validação só num setter não adiantaria, porque o Jackson (deserialização do JSON) usa o construtor vazio + setters para montar o objeto de request, e o controller só chama o construtor "de verdade" (com todos os campos) ao montar a instância que será persistida; então validar no construtor garante que nenhuma instância inválida de `Conteudo` seja passada adiante para o repository. Já a garantia de créditos não ficarem negativos não é uma validação de "objeto malformado" e sim uma **regra de negócio do fluxo de aluguel** — por isso mora no método `Usuario.alugar()` (que testa `temCreditosSuficientes(p)` antes de debitar), não no construtor de `Usuario` nem no setter de `creditos`. Validar só em um lugar não é suficiente porque cada camada é acessada de formas diferentes: o construtor protege contra objetos criados errado desde o início, o método de negócio protege contra uma transição de estado inválida (um débito que deixaria o saldo negativo), e sem as duas camadas, bastaria alguém montar o objeto por outro caminho (ex.: um novo endpoint, um teste, um script) para escapar da regra.

### 6. Abstração e interface (Aulas 8 e 9)
`Conteudo` é uma classe abstrata porque representa um conceito que nunca existe "sozinho" no sistema — todo conteúdo real é necessariamente um `Filme`, uma `Serie` ou um `Documentario`, e por isso `Conteudo` centraliza o que é **comum** a todos eles (título, categoria, duração, classificação etária, disponibilidade) e força, via `calcularPrecoAluguel()` abstrato, que cada subclasse defina sua própria regra de preço — é uma relação de "é um" (`Filme` é um `Conteudo`). Já `Promocionavel` é uma interface porque representa uma **capacidade opcional**, ortogonal à hierarquia de herança: nem todo `Conteudo` participa de promoção (`Documentario` não participa, conforme o contrato), então essa capacidade não podia estar em `Conteudo` nem depender de herança — é uma relação de "pode fazer", implementada só por quem precisa (`Filme implements Promocionavel`, `Serie implements Promocionavel`). Se o Documentário passasse a ter promoção, a mudança seria isolada e pequena: bastaria fazer `public class Documentario extends Conteudo implements Promocionavel` e implementar `aplicarPromocao(double preco)` nele — nenhuma linha de `Conteudo`, `Filme`, `Serie` ou de `calcularPrecoPromocional()` (que já verifica dinamicamente `if (this instanceof Promocionavel)`) precisaria mudar. Isso mostra que o design atual segue bem o princípio aberto/fechado (open/closed): o sistema está aberto para essa extensão sem exigir alteração no código já existente e testado.
